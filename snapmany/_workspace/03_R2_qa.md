## D. API 계약 일관성 (요청/응답 shape 교차)

### 요청
- backend `route.ts` line 88-89: `(body as Record<string, unknown>).image` / `.styleId`
- architect §6 명세: `{ image, styleId }`
- → **키 이름 일치** (`image`, `styleId`).

### 응답
- backend success: `{ ok: true, styleId, imageUrl }` (line 134)
- backend error: `{ ok: false, styleId, error }` (line 76, 94, 103, 117, 125, 137, 141, 145, 151)
- architect §6 명세와 **완전 일치**.

### frontend GenerationItem 타입 (R3가 응답을 매핑할 대상)
```ts
type GenerationItem = {
  id: string;          // 클라이언트 발급
  styleId: string;     // ← API 응답의 styleId
  styleLabel: string;  // STYLES.find(...).label
  status: GenerationStatus;
  imageUrl?: string;   // ← API 응답의 imageUrl (ok: true 시)
  error?: string;      // ← API 응답의 error (ok: false 시)
};
```
- backend 응답 4 필드 중 `styleId`/`imageUrl`/`error`는 frontend가 그대로 소비. `ok`는 R3 reducer가 status로 변환(true → "completed" / false → "failed"). **shape 완전 정합.**
- HTTP 상태 코드 매핑 (200/400/413/500/502/504/405): R2 backend §4가 진실 소스, frontend는 R3에서 `status` 변환 외 별도 분기 없이 `error` 문자열을 그대로 노출하면 충분.
