## E. API shape 확정

backend가 `_workspace/03_R1_backend_done.md` §4에서 동결한 응답 shape:

```ts
type GenerateResponseOk  = { ok: true;  styleId: string; imageUrl: string };
type GenerateResponseErr = { ok: false; styleId: string; error: string };
```

architect `_workspace/00_architect_decisions.md` §6 API 계약과 **완전 일치**:

```ts
type GenerateResponseOk  = { ok: true;  styleId: string; imageUrl: string };
type GenerateResponseErr = { ok: false; styleId: string; error: string };
```

- 요청 body shape (`{ image, styleId }`) 동일.
- 1요청 = 1스타일, 클라이언트 측 N개 병렬 fetch — 양 문서 합치.
- HTTP 상태 코드(200/400/413/422/500/502/504)는 architect 문서에는 없고 backend가 R2 진입을 위해 §4에서 신규 명세. 이는 §6의 "응답 형식"을 확장(보강)할 뿐 상충 없음 → **R2 backend가 그대로 구현, 진실 소스는 backend §4**.
- `imageUrl`은 `replicate.delivery` / `pbxt.replicate.delivery` 호스트. `next.config.ts`의 `images.remotePatterns`는 architect 문서 §10에 `replicate.delivery`만 명시되어 있었으나 backend §4는 두 호스트를 모두 허용 중이라고 보고 — **R2 진입 전 architect/backend가 `next.config.ts` 실제 상태를 한 번 확인 권고** (qa 단계에서는 검증 불요, R2 frontend가 `<Image>` 렌더 시 자연스럽게 노출됨).

→ **API shape 확정. 충돌 없음. backend §4를 R2의 진실 소스로 채택.**
